## 0. What this document checks and what it does not

**What it checks** — the deliverables that come out when the spreadsheet pipeline has run in an actual Task. Following the confirmed spec (D-58 · as amended by D-59), it checks **the deliverables of the two stages separately**.

| Stage | Deliverable (D-59 "구성" (composition) · "사람 확인" (human confirmation)) | The B that checks it in this document | Sections checked |
|---|---|---|---|
| ① **Layout work** | Layout document (md) — reading and analyzing the input + deciding what to make/change and in what shape. Place = the design gate's `log/T{N}_<job>/design-spec.md` | **Layout B** | §4 (LC · LT · LB) |
| ② **Output work** | The working-copy xlsx in `output/` made on the basis of the layout + the change record file (a separate file inside that Task's output, one section per version) + the build summary | **Output B** | §5 (OC · OT · OB) |

B verifies **twice** (D-59 "에이전트" (agents)). Each of the two Bs checks only the sections of its own stage.

**Order of the stages and the criteria Bs** (D-61 G-16 — it replaces D-60 G-13 "once, at the start of the Task" · the first line and the last line are D-69 U-1 (가) · U-2 (가)):

```
(Z · user negotiation → ★ Spec confirmation)
→ layout-criteria B → ★ layout Criteria approval → layout A → layout B → ★ Design (layout) approval
→ output-criteria B → (★ output Criteria approval — chosen per Task · if there is a gray area it is opened even when skipped) → output A → output B → ★ Final acceptance
→ preference-recording B (always once after ★ Final acceptance — whether there is anything to accumulate is decided by that B)
```

- **The negotiation at the very front · ★ Spec confirmation** are row 1 · the ★ row of the step table of the definition (`z/pipelines/spreadsheet.md`) (D-69 U-1 (가) — the user decided to leave them as they are). The "confirmed spec" in which the criteria B finds the target and the skills (§3.2 · §7 ②) comes from here. It is not a verdict step, so it is not counted among the seven steps of G-16.
- **The verification criteria are written per stage, before that stage.** The layout-criteria B looks only at the spec and the input; the output-criteria B looks at **the approved layout** as well, and writes that stage's merged criteria (§7). The B that writes the criteria and the B that judges by those criteria are different calls (`b/common-rules.md` §7).
- **The Criteria approval ★ has two places** (D-62 G-18 (ㄱ)). ★ layout Criteria approval is always obtained. ★ output Criteria approval is **chosen per Task** — at the ★ layout Criteria approval, Z asks "whether to also obtain the output Criteria approval / or skip it", and the user's answer is left in the ledger checkpoints. In a Task that skipped it, that answer is the basis for writing the output merged criteria (§7 ①). The purpose is the convenience of third parties (the user's words — D-62). **However, even in a Task that decided to skip, if the output-criteria B raises a gray area for a person to decide (including the case where it stopped the merged criteria), that Task opens ★ output Criteria approval** (D-63 G-20 (ㄱ) — §7 ① fourth bullet).
- **The preference-recording B after ★ Final acceptance** (D-63 G-21 (ㄴ) · D-69 U-2 (가)) — one short B call that Z makes **always once** copies the user's verbatim words left in the ledger checkpoints into `references/user-preferences.md`, and **may also write the user preferences that B has identified**. That file is written divided into **two sections** — §3 What the user directly requested / §4 B's inferences (user preferences that B inferred + output B's own preference remarks) (D-64 G-22 (ㄴ)). It is a call that does not judge and does not use the items of this document. Who · reads what · and writes how is in §1 · §2 of that file. It is also that B that decides whether there is anything to accumulate — if there is nothing, it adds no line and returns that fact (item 7 of §2 of that file).
- **There is no verdict synthesis step (synthesizing B).** The verdicts of the two Bs are each material for a different ★ (Design approval · Final acceptance). Instead, **output B checks wording (vocabulary that does not sound like AI) · design · readability together** (D-61 G-17 → §5.1.7).

**What it does not check**
- The pipeline definition (`z/pipelines/spreadsheet.md`) · the A rules (`a/tracks/spreadsheet/`) themselves → the criteria of the new-pipeline track check them.
- **Domain facts of the content** inside the spreadsheet (whether circuit values · test verdict values · business figures are right) → they differ by domain, so they are not track items. If the Task spec fixes the source material, they are attached as **the third layer (items for this Task)** (§6 candidate list).
- The meaning of verdict words · verdict values · severity → the common layer.

## 1. Verdict values · severity · overall rule

This track does not define them separately. **The three verdict values (Pass/Conditional/Fail · including doc-gap ⚠️) · the three severity grades (Required/Recommended/Optional) · the overall verdict rule follow `b/common-criteria.md` §1·§1.1·§2·§6 as is.** The merged criteria carry that original text along with them (common §8).

Points to note in this track:
- A spreadsheet deliverable is **a document that people rely on cell by cell** (testers · vendors · designers). A cell range that was not checked cannot be a basis for Pass — for a range checked by sample, write the range in the result (common §6.3).
- **The overall verdict is given separately per stage.** Layout B's overall verdict is about the layout document, and output B's overall verdict is about the output. Do not mix the results of one stage into the count of the other stage's overall verdict. There is no synthesizing B that combines the two overall verdicts (D-61 G-17).
- The wording · design · readability items (§5.1.7) enter output B's overall verdict **under the same weighting rule** — they are not counted separately (they are also counted under common §6 "3 or more Recommended → ❌" — **D-62 G-19 (ㄱ) confirmed**: OC-20·22·23·24 Recommended · OC-21 Optional).
- **B's preference remarks are not put into the verdict** (D-62). Write them only as an X-N memo in the report. Into `references/user-preferences.md`, after ★ Final acceptance, the **preference-recording B** copies, in divided sections, the user's verbatim words (§3 of that file — What the user directly requested) and the user preferences B has identified · output B's preference remarks (§4 of that file — B's inferences) (D-63 G-21 (ㄴ) · D-64 G-22 (ㄴ) — §0 · the preamble of §5.1.7 · §1 · §2 of that file).
- **An item that no applicability condition (§3.3) catches** is left as "Not applicable (which condition is not met)" and is not counted in the tally or the overall verdict (the same way as the handling of C-D1 in common §4.1).

### 3.2 How a Task pulls in skills

One Task runs on **one or more layout skills + the output skills of the same targets** (e.g. a Task that fills in one table = `layout/table` + `output/table`. A Task that modifies a table and a block diagram together = all four).

- What is applied to **layout B** = all of §4.1 LC + the sections of the layout skills that Task used (§4.2·§4.3).
- What is applied to **output B** = all of §5.1 OC (including wording · design · readability OC-20~24) + the sections of the output skills that Task used (§5.2·§5.3).
- Which skills are used is found in the **Task spec**, and the layout document confirms it (LC-2). At the time of the layout merged criteria, if the spec has no target or can be read two ways, raise it as a gray area (do not choose by guessing). The output merged criteria choose the output skill sections according to **the LC-2 decision of the approved layout** (§7).
