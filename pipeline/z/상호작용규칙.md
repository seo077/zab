# Z 상호작용 규칙 — A·B와 주고받는 법

> Z가 A·B에게 일을 넘기고 결과를 받을 때의 규칙. **B에게 지시하기 전에는 반드시 §3을 읽는다.**

---

## 0. 이 문서의 뼈대

```
§1  두 가지 실행 모드          — 창을 여러 개 여느냐, Z가 서브에이전트를 돌리느냐
§2  A에게 넘길 때              — 넉넉하게 준다
§3  B에게 넘길 때              — 아껴서 준다 (정보 상한이 있다)
§4  여러 명을 동시에 돌릴 때    — 파일 충돌 방어
§5  B가 여럿일 때의 최종 판정
§6  결과를 받아 기록할 때
```

## 1. 두 가지 실행 모드

**두 모드는 같은 파이프라인 정의를 쓴다.** 단계도 같고, 담당도 같고, **멈추는 자리도 같다.**
다른 것은 딱 하나 — *세션을 사람이 여느냐, Z가 여느냐.*

| | 모드1 — 창 여러 개 | 모드2 — Z가 서브에이전트 구동 |
|---|---|---|
| 세션을 여는 주체 | 사람 | Z |
| A·B에게 지시가 닿는 법 | Z가 쓴 호출 메시지를 사람이 복사해 새 창에 붙여넣음 | Z가 그 메시지를 그대로 서브에이전트 프롬프트로 넘김 |
| 결과가 돌아오는 법 | 사람이 결과를 Z 창에 붙여넣음 | 서브에이전트가 끝나면 Z가 결과를 받음 |
| 여러 개 동시 진행 | 사람이 창을 여러 개 염 | Z가 동시에 띄움 |
| 적합한 때 | 중간에 사람 판단이 잦을 때 · 긴 대화가 필요할 때 | 갈래가 깨끗이 나뉘고 반복이 많을 때 |

### 1.1 왜 "멈추는 자리"가 같아야 하는가 — 가장 중요한 규칙

**서브에이전트는 작업 도중 사용자와 대화할 수 없다.** 이건 취향이 아니라 도구의 구조적 성질이다.
그러니 사람 확인이 필요한 자리에서는 **에이전트 호출 자체를 둘로 쪼갠다.**

```
(X) 틀린 방식 — 한 번에 시킨다
    B 호출: "검증 기준을 만들고 → 사용자 승인받고 → 그 기준으로 검증해줘"
    → 서브에이전트는 사용자에게 물을 수 없다.
      혼자 승인한 셈 치고 넘어가거나, 승인 단계를 통째로 건너뛴다.

(O) 맞는 방식 — 확인 지점에서 끊는다
    B 호출 ①: "검증 기준을 만들어라. 만들고 끝내라."
        ↓
    ★ Z가 결과를 사람에게 보인다 → 사람이 고치거나 승인한다
        ↓
    B 호출 ②: "승인된 기준으로 산출물을 검증하라."   ← 새 세션
```

파이프라인 정의의 단계표에서 **★ 표시가 붙은 줄이 바로 이 끊는 자리**다.
모드1에서도 같은 자리에서 끊는다 — 그래야 두 모드가 같은 결과를 낸다.

> ★ 지점에서 Z가 할 일: 앞 단계 산출물의 **경로를 사람에게 알리고**, 사람이 직접 열어보게 한다.
> Z가 내용을 요약해 "이렇다"고 대신 말하지 않는다. 요약은 사람의 확인을 무디게 한다.

수정 회차에 사용자가 구체 변경 범위와 다음 행동을 이미 허용했다면 §6.4의 조건부 진행 권한을 적용할 수 있다. 직접 확인 승인과 구분해 기록하며, 역할 호출은 여전히 ★에서 끝나고 Z가 다음 새 세션을 배치한다. 조건부 진행은 사용자 답이나 수동 실행 결과를 만들어내지 않는다.

### 1.2 모드2에서 특히 조심할 것

- 서브에이전트에게 넘기는 프롬프트는 **모드1에서 사람에게 붙여넣게 했을 메시지와 글자 그대로 같아야 한다.** 모드2라고 줄이지 않는다.
- 서브에이전트는 자기 세션이 끝나면 기억이 사라진다. **다음 단계에서 필요한 것은 전부 파일에 남기라고 지시**한다.
- 서브에이전트의 응답을 Z가 그대로 사람에게 옮긴다. Z가 다듬으면 그건 이미 Z의 말이다.
- **세션이 외부 사정(API 한도 429 등)으로 끊기면** — 지시를 바꾸지 않고 다음 순서로 잇는다.
  ① Z가 쓸 곳 상태를 확인한다 (`git status` · 쓸 곳 파일 존재 여부 · 쓸 곳 밖 변경 없음).
  ② 같은 세션을 재개할 수 있으면 **같은 세션을 재개**한다. 재개 메시지에는 "끊겼다 · 같은 지시 그대로 · 쓸 곳 현황" 만 싣고 **새 정보를 보태지 않는다** (B라면 §3 상한 그대로).
  ③ 재개할 수 없으면 **같은 호출문**으로 새 세션을 연다 (B는 fresh 유지 · 직전 부분 산출물이 있으면 그 경로만 MR-2에 더한다).
  ④ 중단·재개 사실을 `log/실행로그.md` 와 `log/manifest.json` history 에 적는다 — 판정·결과 기록은 완료된 회차 기준으로 한다.

### 1.3 Codex와 Claude의 호출 수단

업무 역할·MR/VB 상한·파일 소유권·★는 위 규칙 그대로다. 이 절은 클라이언트 호출 수단을 연결한다.

- Codex 모드2는 Z가 보관한 호출문 **전문 그대로** 새 `collaboration.spawn_agent`에 전달하고 `fork_turns="none"`을 명시한다. 사용자가 지정하지 않은 model·reasoning_effort override는 생략한다. 아래 구성 선택의 실제 응답 ②/③은 해당 preset 지정이며, preselect나 무응답은 지정이 아니다. 모드1의 전문 파일·SHA256와 연결한다. A/B와 승인 뒤 다음 단계는 각각 새 세션이다.
- fresh 대화와 자동 로딩 지침은 별개다. 프로젝트/글로벌 AGENTS와 훅의 추가 문맥, 실제 초기 응답·읽기 흔적을 함께 관찰한다. B에게 A/Z 대화·평가나 전체 설치 안내를 추가 전달하지 않는다. 독립 세션 기능이나 증거가 부족하면 미확인을 남기고 모드1 전환·재실행을 사용자와 협의한다.
- Claude를 선택한 모드2는 프로젝트에 등록된 공식 `claude mcp serve`의 새 Agent를 사용한다. `subagent_type="general-purpose"`, description·독립 prompt를 전달한다. 별도 요청 없는 model/effort는 생략한다(아래 구성 선택의 실제 응답은 지정으로 기록). 일반 역할의 name/isolation은 생략한다. A/B는 각각 새 Agent이며 SendMessage로 이전 역할을 재개하지 않는다. isError·내부 status/content·반환 ID를 확인하고 중단은 해당 ID의 TaskStop을 사용한다.
- 도구 실패나 시간 초과는 역할 결과·사용자 수락이 아니다. 외부 중단의 같은 단계 복구만 §1.2를 따르며 ★ 뒤 다음 단계는 새 호출이다. MCP cwd를 승인 범위와 대조하고 거절된 Codex 작업을 Claude로 우회하지 않는다.
- 자동 실행 검토·sandbox 권한과 ★ 업무 승인은 서로 대체하지 않는다. 클라이언트 사용법은 [Codex운용.md](Codex운용.md)에 있고 B에게는 해당 단계에 허용한 경로만 전달한다.

### 1.3.1 모드2 구성 선택 — 두 Z 계열 공통

현재 Z의 계열·호스트를 먼저 확인한다. 이 선택은 A/B 구성용이며 Z 자신을 재시작하거나 모델을 바꾸지 않는다. 설치된 CLI와 실제 호출 도구의 지원값을 조회하여 버전·명령·출력·시각·실패를 기록한다. 도구 선언 목록을 설치 CLI 모델 목록으로 대신하지 않는다.

| 번호 | 선택 | A/B 구성 |
|---|---|---|
| ① | 직접 고르기 | A 계열(Claude/Codex) → 모델 → effort, 이어 B 계열 → 모델 → effort를 실제 실행 가능한 목록에서 각각 선택 |
| ② | 같은 계열 — 기본 | Z·A·B가 같은 계열. Claude는 설치 버전에서 최신 Opus를 가리키는 opus 별칭·xhigh, Codex는 설치 CLI 목록으로 확인한 최신 astra·high |
| ③ | Z·A 동일, B 다른 계열 | A=Z, B=반대 계열. 모델·effort는 ②의 해당 계열 값 |

선택형 질문 도구를 현재 세션에서 확인하여 사용한다. 기본 미리 선택은 ②로 하되 UI가 preselect를 지원하지 않으면 ②를 기본 추천으로 표시한다. 추천을 첫 항목에 두어야 하는 UI에서는 ②를 먼저 표시하고 번호 의미를 유지한다. UI가 없으면 같은 번호·영향을 텍스트로 묻는다. 미관찰은 미지원이 아니다. 화면 표시와 응답 수신은 도구 선언과 별도로 기록한다. 기본 선택은 실제 답이 아니며 응답 전 해당 구성 호출을 시작하지 않는다.

③은 반대 계열 CLI 설치가 확인될 때만 선택 가능하게 제시한다. 미설치·조회 실패·미확인은 구별하며 활성화 불가 이유를 표시한다. 한 계열만 설치된 경우 ②를 사용할 수 있다. ① 역시 설치·모델·effort·호출 도구 지원이 확인된 후보만 제시한다. 최신 여부 또는 effort 지원이 확인되지 않으면 null과 이유·조회 증거를 남기고 사용자 선택으로 돌린다. xhigh를 high로, astra를 다른 모델로 조용히 대체하지 않는다.

| Z | A | B | 선택 경로 |
|---|---|---|---|
| Claude | Claude | Claude | ① 또는 ② |
| Claude | Claude | Codex | ① 또는 ③ |
| Claude | Codex | Claude | ① |
| Claude | Codex | Codex | ① |
| Codex | Claude | Claude | ① |
| Codex | Claude | Codex | ① |
| Codex | Codex | Claude | ① 또는 ③ |
| Codex | Codex | Codex | ① 또는 ② |

표는 설치·지원 확인 후의 경로이지 실제 실행 증거가 아니다. 한 계열 설치에서는 그 계열 A/B만 제공한다. 모든 행은 UI 지원/미지원 시 각각 선택형/번호형을 쓰며 지원 불일치면 해당 호출을 보류한다. 사용자에게 지원값 직접 선택(구성 변경 기록), 환경 준비 후 preset 유지(대기), 모드1 전환의 영향을 제시한다.

호출 전 선택 모델·effort를 실제 도구 스키마와 대조한다. Codex Z → Codex는 새 spawn_agent의 fork_turns=none과 확정한 model/reasoning_effort를, Codex Z → Claude는 기존 공식 MCP 새 Agent의 model/effort를 대조한다. Claude Z → Claude는 새 Agent 스키마, Claude Z → Codex는 기존 codex-companion의 --model·--effort 및 독립 전문·세션·로그 자리를 확인한다. 지원값이 어긋나면 해결 전 실행하지 않는다. 설정 변경·설치·권한 우회 허가는 이 절로 생기지 않는다.

Z는 Task 배정/모드2_구동구성_R{M}.json에 version, Z 계열·호스트, mode, UI 도구/번호형, preselected=2(의도한 기본값)와 실제 preselect 지원 여부, 실제 답 원문·출처·시각·선택 번호, A/B의 계열·model_selector·resolved_model_id·effort, CLI 경로·버전·목록 증거·시각·설치 상태·capability 증거·적용 호출 범위·replaces를 기록한다. 미실측 resolved_model_id는 null과 이유를 둔다. 고정 모델 ID는 이 실행 사건 기록에만 두고 규정 본문에 박지 않는다. 실제 호출 인수·전문 지문·반환 ID는 Z 실행 기록으로 연결한다. 이 파일 전체를 B에게 자동 배정하지 않고 필요한 실행 사실·권한만 중립 구획으로 제공한다.

선택 기록이 없으면 기존 override 생략을 유지한다. 새 선택 절차 진행 중이면 응답을 기다리며, 이미 명시된 구성은 승인 범위에서 유지한다. ★ 뒤 다음 역할은 새 세션이다.

### 1.3.2 B 호출 전 자동 문맥·커밋 제목

Claude Code Agent 모드2와 Codex 모두, Z는 B 호출 직전 커밋 제목·장부의 자동 노출용 새 기록에 승인·잠정·예상 판정 등 힌트를 보태지 않는다. 과거 승인·판정 원문은 지우거나 다시 쓰지 않는다. B 호출 전 Z가 만드는 커밋 제목은 `T{N}: <단계> record`처럼 중립 문면을 사용하고 승인·잠정·격하·판정 기호·결정 내용을 넣지 않는다. 이는 제목 규칙이며 커밋 본문 금지로 확대하지 않는다. 요청 없는 commit/push를 실행할 권한도 아니다. B 호출에는 §3.5의 문맥 공개 상용구를 넣는다. 문맥 제거 성공을 보장하지 않는다.


## 2. A에게 넘길 때 — 넉넉하게 준다

A는 맥락을 알아야 만들 수 있다. **아끼지 않는다.**

| # | 넣을 것 |
|---|---|
| A-1 | 이번 단계가 무엇을 하는 단계인지, 왜 하는지 (배경) |
| A-2 | 관련된 사용자 결정·합의 **원문 그대로**. 수치·고유명사는 변형 금지 |
| A-3 | 읽을 자료 경로 · 쓸 곳 경로 (파이프라인 정의의 그 칸을 그대로 옮긴다). 입력 준비 원본·공통 추출본·지문·읽기 관찰을 연결한다(§3.5). 임시 파일 자리(역할별 세션 임시 또는 output/T{N}_<작업명>/tmp/<역할>_<회차>/, 제출 전 자기 파일 정리)와 도구 로그 자리(로그 위치 환경값 지원 시 실행증거 안, 불가 시 실제 위치·개수·이유 기록)를 각각 명시한다(§3.6) |
| A-4 | Z 본인의 견해·우려·발견 — `[잠정]` 을 붙여서. 지시가 아님을 밝힌다 |
| A-5 | 넘기기 전 **사양이 확정됐는지 확인**한다. 사양이 흐린 채로 넘기면 A는 기존 자산을 보고 사양을 지어낸다 |
| A-6 | B 단독 영역(검증 규칙·검증 기준)에 A를 들여보낼 때는 **"폴더와 빈 파일까지만, 본문 진입 금지"** 를 문장으로 못박는다 |
| A-7 | **위임 절차** — "원래 못 하게 해둔 일을 사용자가 이번만 허락"할 때, 그 위임을 지시 메시지에 담고 **증거 3요소**를 함께 적는다: ① 허락 출처 ② 날짜 ③ **사용자 발언 원문 그대로.** ③이 빠지면 나중에 위임 사실을 재구성할 수 없다. 단, 위임으로도 못 넘는 선이 있다 — **검증자 본문(B 단독 영역)은 사용자가 위임해도 A가 진입하지 않는다** (`a/공통규칙.md` §1.2와 일관) |
| A-8 | **저장소 진입 경로** — 지시에 **저장소 절대경로 + A가 읽을 부팅문 경로**(`a/부팅.md` 등)를 담는다. 모드1·모드2에 똑같이 싣는다. 프로젝트 `CLAUDE.md` 자동 로드에 "진입 수단"으로 기대지 않는다(덤일 뿐). 저장소 경로는 절대경로로 명시한다 |
| A-9 | **자체 점검 지시** — 제출 전에 자기 산출물을 돌려보고(존재 · 실행 · 재현) 고친 뒤, 그 결과를 구현요약의 **별도 절 "자체 점검"** 에 `a/공통규칙.md` §5 자체 점검 틀대로 남기라고 적는다. 자체 점검은 존재·실행·재현 및 구현자의 오류 예방·수정이며 독립 판정은 B 몫이라는 경계도 넣는다. 돌아가는 것이 아닌 산출물(문서 등)이면 해당 없음, 돌아가야 하는데 도구·권한이 없어 못 돌렸으면 미완으로 적게 한다 |
| A-10 | **설계 게이트의 승인 기준 전달** — 최초·수정 회차 모두 기준 개정·승인 뒤 해당 판을 고정해 설계를 배정한다. B가 작성한 설계용 발췌/대상별 기준 파일 또는 승인 문면 전재를 사용한다. 원 기준 경로·r·지문·승인 범위, 포함 ID(D-*·해당 C-D1 등)·원문 위치, 적용 조건·주석·외부 정의의 대응, 전달 파일 경로·지문·전달 방식을 함께 고정한다. 항목만 떼어 조건이 사라지지 않게 B가 작성한다. A에게 배정된 전달면만 읽히며 b/·원 기준 전체를 열 권한을 주지 않는다. 해시·줄 대조는 판 식별/차이 사실이며 내용 정확성·완전성·설계 영향 없음의 판정이 아니다. 과거 호출문 연쇄 참조를 기본으로 쓰지 않는다 |

### 2.1 A 재작업 인계

지적 원문과 그 출처, 승인 사양·설계·기준 전달면의 판, 허용된 읽기/쓰기 경로, 회차별 제출 사본·구현요약 경로를 전달한다. A가 읽을 수 없는 B 본문은 A용 전달 문면으로 배정한다. 지적 고침 뒤 배정 산출물 전반·원인·연관 영향 재검토와 별도 “전반 재검토” 절을 지시한다. 고친 것·유지한 것·미확인·범위 밖 요청을 남기게 하며 사양 변경·타 역할/Task 파일·새 설계 결정은 별도 결정으로 돌린다. A 자체 목록으로 B의 독립 재검증 범위를 한정하지 않는다.

## 3. B에게 넘길 때 — 아껴서 준다

B는 **혼자 판단해야** 값이 있다. 미리 알려준 만큼 B의 눈은 흐려진다.
**A에게 주던 것을 그대로 B에게 주면 안 된다.** 역할이 다르다.

### 3.1 넣을 수 있는 것 — 이 네 가지가 상한이다

| # | 항목 | 내용 | 금지 |
|---|---|---|---|
| **MR-1** | 의뢰 Task·단계 식별자 | `T{N} / <단계> R{M}` 표기 (재작업이면 `R{M}` 을 붙인다) | Task·단계 식별자 그 자체만. **Task·단계 내용 요약 금지** |
| **MR-2** | 검증 대상·권한·판독 출처 경로 | 중립적인 파일/루트 경로와 고정 판·기준선 식별자. 실제 회차별 권한 원문·전후 자료 경로를 포함(§6.2). 장부가 필요하면 전체 장부 대신 §3.3의 사실 발췌 경로를 배정 | 본문 요약·구조 노출·중요 라인 인용·A/Z가 선별한 중요 변경 목록 금지. 실제 변경은 **B가 직접 도출** |
| **MR-3** | 의뢰 출처·승인 | 사용자 명시 승인 여부 + 의뢰 일자 | A 자평·Z 추측·예상 판정 포함 금지 |
| **MR-4** | 직전 회차 메타 (재검증일 때) | 직전 회차 종합 판정 **한 단어** + 직전 보고서 파일 경로 | 직전 회차의 지적 항목·근거·점검 포인트 본문 인용 금지. **B가 직접 Read** |

이 네 가지 밖의 정보를 넣고 싶어지면, 그건 대개 아래 §3.2에 걸린다.

### 3.2 넣으면 안 되는 것 — 다섯 가지 위배 패턴

메시지를 다 쓴 뒤 스스로 훑는다. 하나라도 걸리면 **초안 작성을 멈추고 사용자에게 보고한 뒤 §3.1의 네 항목으로 다시 쓴다.**

| # | 위배 패턴 | 왜 안 되는가 |
|---|---|---|
| **VB-1** | 검증 점검 항목을 미리 제시 (예: "아래 N항 점검 권장") | 앵커링 — B가 그 목록 안에서만 본다 |
| **VB-2** | 검증 대상의 구조를 미리 요약 (단계 구성·슬롯·필드·식별자 체계 등을 본문 인용 없이 정리해줌) | B가 직접 읽고 파악하는 과정을 건너뛰게 만든다 |
| **VB-3** | 결정사항 본문을 요약해 붙임 | B의 직접 읽기를 우회하는 압축 인용 |
| **VB-4** | A의 자체 평가를 그대로 인용 (예: "A는 문제없다고 봤다") | A의 시각이 B의 출발점이 된다 |
| **VB-5** | "특히 ~을 봐주세요" / "~에 주의해주세요" | 주의를 몰아주면 나머지가 비게 된다 |

> 이 다섯은 **B 의뢰에만** 적용된다. A 의뢰에는 적용하지 않는다 (§2 참조).

### 3.3 B가 스스로 읽는다는 전제

B는 켜질 때 자기 부팅 문서가 시키는 대로 필요한 파일을 스스로 연다.
그러니 Z가 "친절하게" 내용을 옮겨 담을 이유가 없다. **경로만 정확히 주면 된다.**

판정 호출 전 Z는 승인 기준에서 B가 정한 판독/대체 출처·수단과 실제 읽기 배정이 연결되는지 확인한다. 출처가 없거나 역할 경계와 충돌하면 배정을 보충하거나 필요한 결정을 받는다. A 호출 전문에 견해·평가가 섞여 있으면 B에게 넘기지 않고 §6.2의 동일 권한 구획을 고정한 중립 원문을 배정한다. 현재 장부 agents나 A 변경목록으로 당시 권한을 대신하지 않는다.

장부가 필요하면 Z가 Task/배정/B{N}_<단계>_R{M}_장부사실.json을 고정해 경로만 배정한다. source_path·source_sha256·수집시각·task와 원문 필드 위치/값을 연결한다. 필요한 범위의 tasks 현재_단계, agents[].id·role·전용_파일, 산출물 및 history의 task·단계·담당·시각·파일만 투영한다. agents 맡은_범위, 확인지점, 판정, 한_일·메모, 사용자 결정 요약·해석 등 자유 서술은 제외한다. 사실과 평가가 섞이면 의미를 다시 쓰지 말고 허용 사실 칸만 취한다. 기존 manifest 스키마와 C-8은 유지한다. 당시 권한은 §6.2의 중립 권한 원문으로 별도 연결하며 현재 장부로 대체하지 않는다.

### 3.4 모드2에서 더 중요해지는 이유

모드1에서는 B가 이상하다 싶으면 사람에게 되물을 수 있었다. 모드2의 서브에이전트는 되물을 수 없다.
그래서 **Z가 넣은 한 줄이 곧 B의 시야 전체**가 된다. 정보 상한은 모드2에서 더 엄하게 지킨다.

### 3.5 저장소 진입 경로 — 찾아오는 길은 상한과 별개다

지시에 **저장소 절대경로 + B가 읽을 부팅문 경로**(`b/부팅.md` 등)를 담는다. 모드1·모드2에 똑같이 싣는다.
프로젝트 `CLAUDE.md` 자동 로드에 "진입 수단"으로 기대지 않는다(덤일 뿐). 저장소 경로는 절대경로로 명시한다.

> 이건 **"찾아오는 길"**이라 §3.1의 정보 상한(MR-1~MR-4)과 별개다 — 경로를 준다고 상한이 풀리는 게 아니다.
> **상한 자체는 그대로다.** 검증 대상 요약·점검 항목을 §3에 얹는 것은 여전히 금지(§3.2 VB-1~VB-5).

---

A/B 읽기 배정에 원자료·공통 추출본·입력목록의 실제 절대경로와 지문을 연결한다. 준비 절차는 [부팅.md](부팅.md)의 「입력·호스트 준비」를 따른다. 자료 내용 요약을 B에게 덧붙이지 않는다.

B 읽기 상용구: “공통규정 본문이 경로로 지목한 예시 폼도 열 수 있다. 현재 예시 폼은 project_예시/log/T1_예시작업/검증기준.md이며 Z가 템플릿 E의 실제 절대경로로 풀어 배정한다. 누락이면 경로·이유를 반환한다. b/ 전체나 임의 링크의 읽기 허가로 확대하지 않는다.”

B 문맥 상용구: “자동 주입 문맥은 근거에서 빼고 첫 회신 첫 줄에 실제 보이는 초기 문맥 범주와 배정 밖 노출 여부를 적는다. 관찰할 수 없는 문맥은 없었다고 단정하지 않는다.” 이는 정보 상한 밖 내용을 요약해 전달할 구실이 아니다.

### 3.6 B 쓰기 배정 — 재실행·임시·로그

B가 산출물을 실행해야 하는 판은 log/T{N}_<작업명>/검증요약/B{M}_R{K}_증거/재실행사본/을 표준 쓰기 자리로 배정한다. Git은 고정 기준 commit의 지정 산출 범위 추적 파일만 구성한다. 현재 작업 트리·기존 node_modules는 복사하지 않는다. 비Git은 Z가 고정한 제출 원문 사본과 전체 포함 목록·해시로 구성한다. source 종류·고정 판·포함/제외 파일·해시·구성 시각을 남긴다. 링크·외부 의존·누락이나 원문 경계 미정이면 실행을 미루고 원본 실행으로 대신하지 않는다.

설치물·생성물은 재실행사본 안 ignore 규칙으로 제외한다. ignore는 보안 경계나 삭제 허가가 아니다. 도구 상태·로그·실행 전후 증거는 같은 B 증거 구획에 둔다. 문서 읽기만 하는 판에는 재실행사본 불필요를 배정에 적는다. 코드 갈래 검증기준이 생길 때 그 갈래로 옮길 예정이며 이번 규정으로 새 갈래를 만들지 않는다.

A/B 호출에는 두 자리를 각각 명시한다: 임시 파일은 역할별 배정 세션 임시 또는 output/T{N}_<작업명>/tmp/<역할>_<회차>/, 도구 로그는 해당 역할 실행증거 안. 제출 전 자기 임시 파일만 지우고 자기 요약에 기록한다. 쓰기 배정 밖 일시 쓰기는 OS 임시 폴더만 허용한다. 로그 위치 환경값을 받으면 증거 안으로 지정하고(예: npm_config_logs_dir), 불가하면 실제 위치·개수·이유를 기록한다. 관찰 불가 값은 null과 이유로 남긴다. A 설명과 도구 원문 출처를 구분하며 권한 거절을 우회하지 않는다.

## 4. 여러 명을 동시에 돌릴 때 — 충돌 방어 3규칙

병렬은 두 층에서 일어난다 — **Task끼리**(T1·T2 동시 진행) 그리고 **한 Task 안 담당끼리**(A1·A2 동시 배치). 어느 층이든 아래 3규칙은 똑같이 적용된다.

| # | 규칙 | 하는 법 |
|---|---|---|
| **P-1** | **한 파일에는 주인이 하나** | 배치할 때 Z가 각 에이전트에게 **쓸 경로를 못박는다.** "알아서 적당한 데 쓰라"고 하지 않는다. Task가 다르면 방(`log/T{N}_<작업명>/`)이 달라 겹치지 않는다 |
| **P-2** | **공동 장부는 Z만 쓴다** | Task 장부 `log/manifest.json` 은 **Z 전용**. A·B는 읽기만. 각자의 요약은 자기 Task 방 안에 `log/T{N}_<작업명>/구현요약/A1_*.md` · `log/T{N}_<작업명>/검증요약/B1_*.md` 처럼 **에이전트별 파일로 분리**한다. Task 방 밖 공용 파일(`log/실행로그.md`·`log/AI 논의사항.md`)도 **Z만 쓴다** |
| **P-3** | **깨끗이 갈라지지 않으면 병렬로 두지 않는다** | 두 갈래가 같은 파일을 건드리거나, 파일이 달라도 한쪽 문면에 다른 쪽 내용이 의존하면 순서대로 돌린다. 기준 개정·승인 뒤 설계의 순서는 수정 회차에도 유지하며 새 동시 진행 예외를 두지 않는다. Task 사이도 같다 — 두 Task가 같은 산출물을 건드리면 의존으로 묶어 순서대로 돌린다. 병렬은 속도를 벌자고 하는 것이지 꼭 해야 하는 게 아니다 |

에이전트 번호 붙이는 법: 같은 역할이 여럿이면 `A1`·`A2`·`B1`·`B2` 로 부르고, **그 번호를 파일 이름에 넣는다.** 번호는 Task 안에서 센다 — 다른 Task의 A1과는 방이 달라 부딪히지 않는다.

## 5. B가 여럿일 때의 최종 판정

여러 B의 결과를 **Z가 합치면, 합치는 순간 Z가 판정한 셈이 된다.** 그건 금지선을 넘는 것이다.

그래서 **종합 B를 한 명 더 둔다.**

```
B1 ─┐
B2 ─┼→  종합 B  →  최종 판정 한 줄  →  Z가 사람에게 전달
B3 ─┘
```

- 종합 B에게는 **각 B의 보고서 파일 경로만** 준다 (§3.1 상한 그대로).
- 어느 B의 의견이 맞아 보이는지 Z가 곁들이지 않는다.
- B가 한 명뿐이면 종합 단계는 건너뛴다.

## 6. 결과를 받아 기록할 때

1. **원문 보존** — 판정과 지적은 B가 쓴 말 그대로 옮긴다. 부드럽게 고치지 않는다.
2. **장부 갱신** — `log/manifest.json` 의 `history` 에 한 줄 append — **어느 Task인지(`T{N}`)를 달아서.** 해당 Task의 상태·현재 단계도 함께 갱신한다 (Z만 쓴다, P-2).
3. **사람에게 전달** — 결과 파일 경로 + 판정 한 줄. 해석은 붙이지 않는다.
4. **다음 단계 판단은 사람이** — 다음으로 갈지, 되돌릴지, 멈출지는 사용자가 정한다. 이미 부여된 권한은 §6.3·§6.4대로 기록·적용하며 새 결정이 필요한 부분만 묻는다.
5. **개선 후보 적어두기** — 이번에 파이프라인 자체가 어긋난 데가 있으면 `개선이력/` 후보로 메모한다. 작업 도중에 고치지는 않는다.


### 6.1 제출·승인 판 연결

설계·검증기준의 매 제출/승인 판 원문은 해당 소유 역할이 복구 가능한 사본으로 남긴다. 산출물 방식은 Task 사양에서 정한다. Z는 Task·단계·역할·호출 R·문서 리비전(기준 r은 별개)·작업/사본 경로·bytes·SHA256·제출 시각·바탕 판·앞 판/복구 출처에 사용자 원문·출처·날짜·승인 범위를 별도 연결한다. 고정 사본에 승인 문구를 덧쓰지 않는다.

사본이 기본이다. 사양에서 Git/버전 저장을 택하면 원문 파일·commit/blob·별도 복원 위치·실제 복원 열람/지문 결과를 남긴다. 해시·변경이력만으로 보존을 대신하지 않는다. 승인 판과 실제 파일이 달라지면 두 판을 보존하고 필요한 새 역할/결정으로 돌린다. Z의 지문/줄 비교를 설계 영향이나 품질 판정으로 쓰지 않는다.

### 6.2 회차별 중립 배정·비교 출처

Z는 호출을 발행할 때 `log/T{N}_<작업명>/배정/<역할>_<단계명>_R<M>_권한.json`과 `호출/<역할>_<단계명>_R<M>.md`를 연결해 고정한다. 경로는 실제 호출에서 구체화한다. 예시가 읽기/쓰기 권한을 자동 추가하지 않는다.

중립 권한 원문에는 Task·단계·역할·회차·날짜/적용 시점, roots, 읽기(전체/구획/메타 구분), 쓰기(구체 파일 또는 배정 폴더), 제외 범위, 실제 호출 경로/지문·동일 권한 구획, 근거 승인 경로/지문, 기준선 목록 경로/지문을 둔다. A/Z의 평가·우려·예상 판정은 넣지 않는다. 도중 권한 변경은 근거·시점·새 판을 별도 보존하고 앞 판을 덮지 않는다.

제작 전에 비교 범위와 원문 사본을 고정하고 제작 후 같은 범위를 다시 수집한다. 파일 행에는 루트·상대경로·종류(파일/디렉터리)·존재·bytes·SHA256·수집 시각을 남겨 신규/삭제/변경/미변경을 구별한다. 숨김·미추적·무시 대상과 제외 범위를 명시한다. Git이면 루트·기준 commit·대상 commit·HEAD·index/working tree·미커밋·미추적 상태를 함께 고정한다. 비Git/추적 밖은 전후 파일 목록·지문·복구 원문을 쓴다. 목록은 내용 복구 사본의 대체가 아니다.

B는 이 실제 전후 자료에서 변경을 직접 도출한다. A의 설명 목록은 납품 설명이며 비교 전체나 B 범위의 상한이 아니다. 기준 B가 정한 판독/대체 출처·수단을 Z가 판정 호출 전에 실제 경로로 배정한다. 불충분하면 현재 장부나 A 목록을 임의 대체하지 않고 보충/결정으로 돌린다.

장부 사실 발췌(§3.3)는 수집 시점의 사실 기록이고 당시 권한 원문은 별도 사건이다. 둘의 경로·지문·시점을 따로 연결한다. 발췌를 위한 Z의 장부 접근은 B의 전체 장부 접근 허가가 아니다.

### 6.3 사용자 답 충돌·대기

같은 응답 안에서 양립 불가능한 선택이 있거나 대상/범위가 모호하게 남으면 충돌 원문·출처·날짜·해당 지점을 제시하고 필요한 선택만 묻는다. 명백한 최신 수정 지시는 반복 승인 없이 원문 권한으로 기록하고 따른다. 무응답은 동의가 아니다.

추가 답이 필요한 동안 확정 사양을 임의 확정하지 않는다. 장부는 기존 `사람확인대기` 상태에 현재_단계·history.메모로 “Z 추가 답 대기”를 구별한다. 사용자가 직접 보류를 고른 경우에만 확인지점 결과를 `보류`로 남긴다. Z의 대기를 사용자 보류 발언으로 만들지 않는다.

### 6.4 조건부 진행 권한

사용자가 **구체 변경 범위와 다음 행동을 이미 허용한 수정 회차**에 한정한다. 직접 문서를 확인한 승인과 기록 종류를 구별한다.

| 기록 필드 | 담을 것 |
|---|---|
| 종류·권한 원문 | 조건부 진행, 사용자 원문·출처·원 지시 날짜 |
| 바탕·허용 범위 | 기존 승인 판/사본·지문, 허용 변경과 객관 조건 |
| 실제 대조 | 적용 판의 실제 전체 변경과 허용 범위를 대조한 전후 자료·결과·미확인 |
| 적용·다음 행동 | 적용 문서 판/지문·적용일, 허용된 다음 단계와 새 역할 호출 |

Z는 이 기록을 별도 사건 파일로 보존한다. 기존 확인지점 결과=`승인`을 사용하되 확인_대상에 적용 판과 조건부 진행 기록 경로, 사용자_말에 실제 권한 원문, 일자에 적용일을 넣는다. 원 지시 일자는 사건 기록에 보존하고 history에 직접 열람 승인이 아닌 조건부 진행 권한 적용임을 명시한다. 새 상태·결과 enum을 만들지 않는다.

일부 설계 항목이 같다는 사실, R2 이상이라는 번호, 사후 무이의만으로 포괄 승인을 만들지 않는다. 범위 밖 변경·새 결정·조건 실패·대조 불충분은 해당 부분의 별도 선택으로 돌린다. 원문이 명확하고 범위·조건이 대응하면 같은 허락을 다시 묻지 않는다. 역할은 제출 후 종료하며 Z가 권한 기록에 따라 다음 fresh 호출을 한다.

엑셀의 기존 출력 기준 승인 생략은 그 정의의 사용자 선택·회색지대·기록 유무 조건을 그대로 따른다. 이 절로 생략 범위를 늘리거나 회색지대 재개방을 없애지 않는다. 회로 사용자 질의 응답·수동 시뮬 결과를 조건부 진행으로 대신 생성하지 않는다.

### 6.5 미확인 후속 중계

B가 제시한 확인 불가 항목·영향·시도/대체 수단·필요 결정을 원문과 출처로 전달한다. 담당·회차·중단/수락은 Z·사용자가 결정해 별도 기록한다. A의 Q-ID나 후속표 등록만으로 현재 필요한 확인이 끝났다고 적지 않는다. 사양·역할·범위가 바뀌면 해당 판과 새 배정을 먼저 연결한다.
