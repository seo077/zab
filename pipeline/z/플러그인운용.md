# 플러그인 운용 — 이 저장소가 ung 플러그인으로 배포됐을 때

이 저장소의 역할 문서는 "저장소가 어느 절대경로에 있는지는 지시가 알려 준다"는 전제로 쓰였다. 이 문서는 플러그인으로 설치된 환경에서 그 경로들이 무엇인지와, 세 명령이 정석 흐름의 어느 구간을 맡는지를 정한다. 역할·금지선·★·정보 상한은 다른 문서 그대로이며 여기서 바꾸지 않는다.

**이 문서와 다른 문서의 경로 서술이 어긋나면 경로에 한해 이 문서가 맞다.** 다른 문서의 "프로젝트 `CLAUDE.md` 에서 저장소 경로를 읽는다"는 절차는 플러그인 환경에서 아래 §1로 대신한다.

---

## 1. 경로 넷

| 이름 | 무엇 | 어디서 아나 |
|---|---|---|
| **P** 파이프라인 저장소 | 플러그인 안의 `pipeline/` — 역할 문서·정의·갈래의 원본 | `/ung:design`·`/ung:build` 첫 블록과 세션 시작 배너가 절대경로로 찍어 준다 |
| **E** 템플릿 루트 | 플러그인 안의 `templates/project/` — 프로젝트 양식과 예시 Task 방 폼(`log/T1_예시작업/검증기준.md`) | 같은 곳 |
| 프로젝트 루트 | 세션을 연 폴더 — `input/` · `output/` · `log/` · `프로젝트지도.md` | 같은 곳 |
| **L** 프로젝트 층 | 프로젝트 루트의 `pipeline/` — 이 프로젝트에서 만든 정의·갈래·개선이력 | 같은 곳 |

- 찍힌 값을 그대로 쓴다. 짐작으로 경로를 만들지 않는다.
- A·B 호출문에는 P와 프로젝트 루트를 **절대경로로** 싣는다(`상호작용규칙.md` A-8 · §3.5). 다른 문서가 `project_예시` 라 부르는 것은 E다.
- 장부 `_meta.pipeline_repo` 의 값 `plugin:ung` 은 "경로는 플러그인이 알려 준다"는 표지다. 경로와 대조하지 않는다.

## 2. P는 읽기 전용, 쓰기는 L에

P는 설치된 사본이다. 플러그인을 갱신하면 통째로 바뀌므로 **어떤 회차에서도 P에 쓰지 않는다.** 다른 문서가 파이프라인 저장소에 쓰라고 한 자리는 전부 L의 같은 상대경로로 읽는다.

| 다른 문서가 말하는 쓰기 | 실제로 쓰는 곳 |
|---|---|
| 파이프라인신설의 출력 세 벌 | `L/z/pipelines/<작업명>.md` · `L/a/갈래별/<작업명>/` · `L/b/갈래별/<작업명>/` |
| 개선이력 | `L/개선이력/NNN_<제목>.md` |
| 갈래 참고자료 가운데 쌓아 가는 파일 (예: 사용자 취향) | `L/<같은 상대경로>` |

"작업 중 pipeline은 읽기 전용"은 L에도 그대로다. L에 쓰는 것은 파이프라인신설이 도는 동안과, 작업이 끝난 뒤의 개선이력·누적 기록뿐이다. `b/` 아래 본문은 L에서도 B만 쓴다.

## 3. 읽을 때 — L이 먼저

- **정의 목록**은 P와 L의 `z/pipelines/` 를 합친 것이다. 사용자에게 보일 때 어느 쪽 것인지 함께 적는다.
- **갈래**는 이름으로 찾는다. L에 있으면 L의 것을, 없으면 P의 것을 쓴다. 호출문에는 실제로 고른 쪽의 절대경로를 싣는다 — A·B가 스스로 갈래를 찾지 않는다.
- **같은 이름이 양쪽에 있으면** L을 쓰되, 그 사실을 사용자에게 알리고 실행로그에 적는다.
- **쌓아 가는 참고자료**는 P의 것(배포 시점의 바탕)과 L의 것(이 프로젝트에서 쌓인 줄)을 둘 다 배정한다.

## 4. L에서 P로 — 올리는 길

L에서 되풀이가 확인된 정의·갈래·교훈은 플러그인 원본 저장소에 변경 제안(Pull Request)으로 올린다. 올리는 것은 사용자의 결정이고, 방향은 프로젝트 → 파이프라인 한쪽뿐이다. Z가 스스로 올리지 않는다.

## 5. 세 명령이 맡는 구간

| 명령 | 구간 | 끝나는 자리 |
|---|---|---|
| `/ung:setup` | 프로젝트 폴더 준비 (스크립트가 한다 — 역할 호출 없음) | 폴더·빈 장부가 생긴 때 |
| `/ung:design` | Z 시작 흐름 → 정의의 단계표에서 **산출물 제작 단계 직전의 ★** 까지 | 그 ★ 승인 기록 |
| `/ung:build` | 제작 단계 → ★ 최종 수락 | Task 마감 |

- 두 명령의 경계는 **★ 자리**다. ★에서 역할 호출을 끝내고 새 세션으로 잇는다는 규칙과 같은 선이다.
- 범용 정의에서 경계는 ★ 기준 승인(설계 게이트 판이면 ★ 설계 승인, 검증 생략 판이면 ★ 사양 확정)이다. 다른 정의에서는 A가 `output/` 에 쓰기 시작하는 첫 단계의 바로 앞 ★다.
- `/ung:build` 는 그 ★의 승인이 장부에 없으면 시작하지 않는다.
- 다른 문서의 "`z` 입력"은 이 환경에서 `/ung:design` 또는 `/ung:build` 다.

## 6. 모드와 호출 수단

- **기본은 모드2**(Z가 서브에이전트를 돌린다)다. 사용자가 모드1을 말하면 모드1로 한다. 두 모드의 호출문은 글자 그대로 같다.
- 모드2의 A는 `ung:a`, B는 `ung:b` 에이전트로 부른다. 둘 다 호출문 전문을 그대로 받는다. 이 에이전트 유형이 보이지 않으면 `general-purpose` 로 같은 전문을 넘긴다.
- A·B는 호출마다 **새 에이전트**다. 앞선 역할 세션에 이어 붙이지 않는다(외부 장애로 끊긴 같은 단계의 재개는 `상호작용규칙.md` §1.2).
- 모델·effort는 **지정하지 않는 것이 기본**이다(Z와 같은 것을 쓴다 — `상호작용규칙.md` §1.3.1의 ②에 해당). 사용자가 구성을 고르겠다고 할 때만 그 절의 선택 절차를 밟는다.
- Codex 어댑터는 이 플러그인에 아직 들어 있지 않다. `Codex운용.md` 는 원 저장소의 운용 기록이며, 이 플러그인에서 Codex를 쓰는 절차가 아니다.
