# 파이프라인 정의 — 범용

> 맞는 정의가 없는 **일회성·탐색 작업**을 Task 하나로 돌리는 **기본 골격**이다. 어떤 특정 작업의 정의가 아니다.
> 한 번 쓰고 말 일은 파이프라인으로 굳히지 않는다 — 그런 일은 새 파이프라인을 만들지 않고 이 골격으로 돈다. **되풀이가 확인되면** 그때 `파이프라인신설`로 올린다 (프로젝트 → 파이프라인, 한 방향).
> 다른 정의와 다른 점은 둘이다 — 무슨 일인지 먼저 합의하는 **협의 단계**, 그리고 판마다 켜고 끄는 **조건부 행**(검증 생략 · 설계 게이트). 정의는 이 파일 하나이며 판에 따라 나누지 않는다.
>
> `T{N}` · `<작업명>` · `<갈래>` 는 변수다 — 이 정의는 임의의 일회성 작업에 쓰이므로 자리를 변수로 두고, Z가 Task를 개설할 때 채운다.

## 머리표

| 항목 | 내용 |
|---|---|
| 목적 | 맞는 정의가 없는 일회성·탐색 작업을 Task 하나로 돌리는 기본 골격 |
| 입력 | ① **시작할 때 있어야 하는 것** = 사용자의 요청(무엇을 하고 싶은지) · 재료(`input/` 의 자료 — 있을 때) ② **1단계·★ 사양 확정에서 확정되는 것** = 합의된 작업 사양(목적·입력·출력) · 검증 여부(기본 = 진행) · 설계 게이트 여부 · 지정 갈래(기본 = 없음) |
| 출력 | ① 프로젝트 `output/` 아래 산출물 — 구체 경로는 ★ 사양 확정에서 정한다 ② Task 방 기록 `log/T{N}_<작업명>/` — `검증기준.md` · (`설계명세.md`) · `구현요약/` · `검증요약/` |
| 쓰는 갈래 | **없음(기본)** — ★ 사양 확정 때 **기존** 갈래(`a/갈래별/`·`b/갈래별/` 에 이미 있는 이름)를 지정할 수 있다. 지정된 갈래는 **Z 호출 메시지에 실려** A·B에게 닿는다 — A·B가 스스로 갈래를 찾지 않는다. `범용` 이름의 갈래 폴더는 없고 만들지 않는다 |
| 예상 단계 수 | 기본 판 **4 (협의 · B1 · A1 · B2) + 사람 확인 4자리.** 설계 게이트 선언 판은 +1 (A1 설계) + 1자리. 검증 생략 판은 −2 (B1·B2) − 1자리 (★ 기준 승인). 셈법 = 번호 행 + ★ 행, 조건부 행은 그 판에서 켜진 것만 센다 |

> **담당 표기** — A1 = 이 판의 설계·구현자 (3·4단계 같은 담당). B1 = 기준을 쓰는 검증자, B2 = 판정하는 검증자. **B1과 B2는 별도 fresh 세션**이다 — 기준을 쓴 눈과 판정하는 눈을 나눈다. 판정하는 검증자(B2)가 한 명이므로 판정 종합 단계는 두지 않는다.
> **번호** — 건너뛴 행의 번호는 비워 둔 채 다음 번호로 간다 (당기지 않는다). 어느 판에서든 "4단계" 는 A1 구현이라, 장부·실행로그의 단계 표기가 판마다 달라지지 않는다.
> **병렬** — 이 골격은 담당을 단계마다 한 명으로 둔다. 여러 담당을 동시에 돌려야 할 만큼 갈라지는 일이면, 그것은 이미 되풀이될 모양을 갖춘 일이다 — `파이프라인신설`로 정의를 따로 만든다.

### 조건부 행 — 판마다 켜고 끈다

| 표시 | 뜻 | 켜고 끄는 자리 |
|---|---|---|
| **[검증 생략 시 건너뜀]** | **2 · ★ 기준 승인 · 5** — 검증을 생략한 판에서는 이 셋을 건너뛴다. ★ 구현 확인 · ★ 최종 수락은 그대로 남는다 | ★ 사양 확정의 "검증 여부" |
| **[설계 게이트 선언 시에만]** | **3 · ★ 설계 승인** — 사양에서 설계 게이트를 필요라 했을 때만 4단계 앞에 붙는다. 선언하지 않은 판은 설계 명세를 만들지 않는다 | ★ 사양 확정의 "설계 게이트 여부" |

- 검증을 생략한 판에서도 **Task 개설 · 장부(`log/manifest.json`) · `log/실행로그.md` · 구현요약은 그대로 남긴다.** 생략은 검증 행 셋만 거른다.
- 검증을 생략한 판에서는 ★ 구현 확인 바로 뒤에 ★ 최종 수락이 온다 — 사용자가 산출물을 보고 수락 여부를 정한다.
- 조건은 ★ 사양 확정에서 그 판에 대해 한 번 정해지므로, ★ 의 자리는 모드1·모드2 어느 쪽에서도 같다.

### 협의(1단계)에서 정하는 넷 — ★ 사양 확정의 대상

1. **사양** — 목적 · 입력 · 출력 (산출물의 `output/` 경로까지) · 산출물 판 보존 방식/경로. 설계·기준의 제출/승인 원문은 소유 역할이 사본으로 보존하고, 같은 복구 효과를 실제 확인한 Git/버전 저장은 사양에서 선택한다. 완료 Task의 후속이면 바탕 Task·완료 판/경로/지문·수락 기록, 변경 차이·보존할 바탕·변경 영향과 확인 범위를 함께 정한다. 설계 게이트는 새 사양에서 고르며 큰 설계 재작성을 일괄 강제하지 않는다.
2. **검증 여부** — **기본값 = 검증 진행.** Z는 아래 셋이 **모두** 해당한다고 판단할 때만 검증 생략을 사용자에게 **제안**한다. 정하는 것은 사용자다.
   - ① 산출물이 최종 결과물이 아니라 다음 단계의 재료일 뿐이다 (예: 웹서칭 결과 — `output/` 에는 남긴다)
   - ② 틀려도 되돌리기 쉽다
   - ③ 규칙·설정 파일을 건드리지 않는다
   - 하나라도 어긋나면 제안하지 않는다 — 검증을 진행한다.
3. **설계 게이트 여부** — 설계를 먼저 확정받아야 하는 작업이면 선언한다.
4. **갈래 지정** — 기본 없음. 기존 갈래의 지식이 있어야 하는 작업이면 그 이름을 지정한다 (머리표 "쓰는 갈래").

순서: **협의**(Z ↔ 사용자, 합의에 이를 때까지) → **사용자 승인** → **Z가 확정 사양을 `log/AI 논의사항.md` 에 적는다** → ★ 사양 확정. Z는 선택지와 견해(`[잠정]`)를 내놓고, 정하는 것은 사용자다.

★ 사양 확정 전에 [Z 부팅](../부팅.md)의 「입력·호스트 준비」에 따라 A/B의 실제 원자료 읽기 수단, 공통 추출본·원본 연결, PDF 도구 설치 확인과 프로젝트 git 추적 여부를 기록한다. 입력 준비는 형식 변환·접근 확인이며 해석·요약·산출물 제작이 아니다.

### 협업의 뼈대 — 정의가 있어도 그대로

- **모드1·2** — 사람이 창을 여느냐, Z가 서브에이전트를 돌리느냐. 다른 정의와 똑같이 고른다.
- **★ 사람 확인** — 표에 미리 찍힌 ★ 밖에서도 새 사람 판단이 필요하면 멈춰 돌린다. 명백한 최신 수정 지시, 충돌/모호한 답, 구체 수정 회차의 조건부 진행 권한은 `../상호작용규칙.md` §6.3·§6.4로 구별한다. 직접 확인 승인과 조건부 진행을 따로 기록하고 ★ 뒤 다음 역할은 fresh 세션이다.
- **기준 먼저** — 검증 진행 판은 최초·수정 회차 모두 2단계 기준 개정 → ★ 기준 승인 → 3단계 설계(게이트 판) → 4단계 구현 순서다. 파일이 달라도 내용이 의존하면 병렬로 두지 않는다. B 작성 설계 전달면의 승인 판·조건·주석·외부 정의와 원문 대응은 `../상호작용규칙.md` A-10을 따른다.
- **A에겐 넉넉히, B에겐 아껴서** — 호출 메시지 규칙은 `z/상호작용규칙.md` §2·§3 그대로. 지정 갈래는 그 메시지에 실어 보낸다.
- **판정은 B2 · 수락은 사용자 · Z는 안 만들고 안 판정** — 금지선 그대로.
- **사용자 격하 — ★ 최종 수락의 공식 선택지** — B2 종합이 ⚠️/❌여도, B2 보고서에 `b/공통규칙.md` §6.5 "[규칙과 실판정이 다름]" 기록이 **있을 때만** 사용자는 그 기록을 근거로 한 단계 격하해 수락할 수 있다. 그 기록이 없으면 이 선택지는 없다. Z는 격하 사실·사용자 원문을 `log/AI 논의사항.md` 와 `log/manifest.json` 확인지점에 적는다. B2 보고서는 고치지 않는다 — 판정은 B2의 원문 그대로 남고, 격하는 수락의 기록이다.

### 재작업과 제출 판

진행 중 재작업을 사용자가 정하면 새 A R{M+1}이 지적 원문·승인 판·허용 경로를 받아 지적 고침과 배정 산출물 전반·원인·연관 영향 재검토를 한다. 구현요약의 별도 “전반 재검토”에 고친 것·유지·미확인·범위 밖 요청과 근거를 남긴다. 사양 변경·타 역할/Task 파일·새 설계 결정은 별도 결정으로 돌린다. ★ 구현 확인에서 종료하고 권한 기록 뒤 fresh B2 재검증으로 간다. B2 범위는 승인 기준·실제 변경·의존 영향·미확인에서 B2가 직접 정한다.

기준 변경이 필요하면 fresh B 기준 개정·승인 뒤 필요한 설계부터 순서대로 돌아간다. 설계·기준의 매 제출/승인 원문과 호출 R/기준 r·사본·지문·사용자 승인 연결은 `../상호작용규칙.md` §6.1, 실제 회차별 중립 권한·판독/대체 출처·전후 자료는 §6.2를 따른다. 이 단계표의 변수 경로는 Z가 실제 호출 전에 구체화한다. A의 설명 목록은 B의 비교 범위 상한이 아니다.

완료 뒤 변경은 앞 완료 판·기록을 보존하고 새 Task의 차이 사양으로 연다. 외부 장애의 같은 진행 단계 재개만 `../상호작용규칙.md` §1.2를 따른다.
