# 검증기준 — T{N} <작업명>

> **이 파일은 폼이다.** 실사용 프로젝트에서 Task 방(`log/T{N}_<작업명>/`)을 열 때 이 폼을 복사해 검증자(B)가 채운다.
> `▶` 로 시작하는 줄은 채우는 법 안내이므로 채운 뒤 지운다. `<...>` 는 자리표시자다.
>
> **세 층 구조** — 검증 기준은 세 곳에서 온다:
> ```
> ① pipeline/b/검증기준_공통.md          어떤 작업이든 늘 보는 항목        ┐
> ② pipeline/b/갈래별/<갈래>/검증기준.md  이 종류의 작업에서만 보는 항목    ┴ 구획 A (참조)
> ③ 이번 Task에만 필요한 항목             이 프로젝트의 사양·합의에서 도출   — 구획 B (추가 작성)
> ```
> 셋을 **이 합본**으로 합친다 — 기본 승인 대상은 이 파일 하나다. 대상으로 분할하거나 설계 전달면을 별도로 두면 **목차·구성 파일·전달 범위와 각각의 판을 승인 대상 목록에 명시**한다. 다만 뭉뚱그리지 않는다:
> **어디까지가 pipeline에서 가져온 것(구획 A)이고 어디부터가 이 프로젝트에서 작성한 것(구획 B)인지** 구획으로 구분해 남긴다.
> 합칠 때의 규칙(중복 정리·충돌 처리·출처 표기)은 `pipeline/b/검증기준_공통.md` §8이 정한다.
>
> **본문은 검증자(B)만 쓴다.** 다른 역할은 이 폼을 복사해 두는 것(빈 파일·머리말)까지만 한다.

| 항목 | 값 |
|---|---|
| Task | `T{N}` |
| 작업명 | `<작업명>` |
| 갈래 | `<갈래명 또는 없음>` |
| 파이프라인 정의 | `<z/pipelines/<작업명>.md 또는 범용 모드>` |
| 리비전 | `r1` |
| 단계·호출 회차 | `<단계 / B<N> / R<M> — 기준 r과 별개>` |
| 상태 | 초안 — ★ 사용자 승인 대기 (이 행은 갱신하지 않는다. 실제 승인 원문·대상 판의 연결은 해당 Task 확인지점 또는 그 구획의 중립 배정본으로 확인) |
| 작성자 | B |
| 사양·바탕 판 | `<사양 경로·판·승인. 완료 Task 후속이면 바탕 Task·완료 판·지문·변경 차이·보존 범위>` |

▶ 리비전은 사용자 피드백을 반영할 때마다 r2·r3…으로 올리고, 맨 아래 §변경 이력에 한 줄씩 쌓는다. 지난 리비전 내용을 덮어 지우지 않는다.
▶ **각 제출/승인 판의 원문 사본**을 B의 쓰기 배정 구획에 보존하고 §판 보존 기록을 채운다. 지문·변경이력만으로 사본을 대신하지 않는다. Git/버전 저장은 사양에서 선택하고 실제 복구가 확인될 때만 쓴다. 호출 R이 올라도 기준이 같으면 r을 자동 증가시키지 않는다. 이 폼의 경로 예시는 실제 읽기/쓰기 배정을 대신하지 않는다.

- **항목을 뽑은 곳**: `<사양·합의 문서 경로와 절>`
- **갈래층 유무**: `<갈래 지정 시 ②층 경로 / 미지정이면 "갈래층 없음 — 두 층 합본" 이라고 적는다>`
- **사용할 판·승인 범위**: `<이 합본 r·목차/대상별 구성·설계 전달면 포함 여부. 승인 기록은 별도 파일에서 해당 판을 연결>`
- **변경 도출 기준선 / 보존 품질 비교 판**: `<전후 비교 범위·시점 / 마지막 통과 판 또는 첫 회차 사양. 둘의 목적을 구분>`

# ━━━ 구획 A — pipeline 에서 가져온 기준 (참조) ━━━

▶ 여기부터 구획 B 표시선 전까지가 **pipeline 저장소에서 온 것**이다. 이 구획의 원본은 pipeline 쪽 문서이며, 여기에는 "무엇을 어느 리비전에서 가져왔고 이번 Task에 어떻게 적용하는지"를 남긴다.
▶ 원본과 다르게 고치고 싶은 것이 있으면 여기서 고치지 말고, 어긋난다는 사실을 §회색지대에 적어 사용자 확정을 받는다.

# ━━━ 구획 B — 이 프로젝트에서 추가 작성한 기준 ━━━

▶ 여기부터가 **이 프로젝트에서 새로 작성한 것**이다 (③층). pipeline에 없는, 이번 Task 고유의 항목만 둔다 — pipeline 층과 같은 말을 반복하지 않는다 (겹치면 어긋날 때 판별 불가).
▶ 각 항목에 **출처(어느 사양·합의 문서의 어느 결정)**를 반드시 붙인다. 출처 없는 항목은 승인 때 근거를 잃는다.

### 판독 방법

▶ 실제 Task에서 쓸 독립 판독 절차를 적는다. B 스킬이 있으면 `pipeline/b/공통규칙.md` §9.3대로 방법·해당 참고 절·지문을 별도 구획에 옮긴다. 판정 B는 승인 합본의 방법을 사용한다.
▶ 바이트 관찰이 필요하면 같은 문서 §4.4대로 직접 읽고 CRLF 쌍·독립 CR/LF·마지막 줄 끝·BOM을 구별한다. 대상 판·도구/환경·명령·값을 남기고 새 도구·의심 결과·중요 수치는 알려진 양성/음성 표본 또는 다른 수단으로 대조한다. 모든 수치의 두 도구 측정을 요구하지 않는다.
▶ 재검증 범위는 승인 기준·실제 변경·의존 영향·미확인에서 판정 B가 정한다. A 자체 점검이나 직전 지적 목록으로 상한을 정하지 않는다. 필수 확인 불가를 후속 등록만으로 충족 처리하지 않는다.

▶ 항목뿐 아니라 조건·주석·참조 정의도 직접 대조한다. 해시는 판 식별자이며 정확성·완전성·설계 영향 없음을 증명하지 않는다. 새 발췌가 기존 승인 범위에 포함되는지 불명확하면 사용자에게 범위를 돌린다. 기준 개정·승인 뒤 그 판으로 설계한다. Z의 지문/줄 비교는 품질 판정이 아니다.

## 진행 권한 기록 연결

▶ 직접 확인 승인과 조건부 진행을 구분한다 (`pipeline/b/검증기준_공통.md` §8.4, 절차 원문 `pipeline/z/상호작용규칙.md` §6). 아래는 Z가 기록한 권한 출처를 연결하는 칸이다. B가 다음 단계를 허가하거나 사용자 발언을 만들어 넣지 않는다.

- 권한 종류·출처: `<직접 확인 승인 / 조건부 진행 / 갈래 정의의 기존 생략 선택 / 승인 전 중 실제 해당 사항과 기록 경로>`
- 해당 판·범위: `<기준 r·사본·지문·사용자 원문/출처/날짜 연결>`
- 조건부 진행이면: `<기존 승인 판·이미 허용된 구체 변경/객관 조건·실제 전체 변경 대조 자료·적용 판/지문·허용된 다음 단계가 있는 Z 기록>`
- 미정·범위 밖 변경·조건 실패: `<별도 선택으로 돌릴 내용 또는 없음>`

▶ 조건부 진행은 이미 구체 변경 범위와 다음 행동을 허용받은 수정 회차에만 적용한다. 일부 행 불변·R2 이상·사후 무이의는 포괄 승인이 아니다. 엑셀작업 기존 출력 기준 승인 생략은 사용자 선택·회색지대·기록 조건을 그대로 따른다. 어느 경우든 기준 작성 호출은 종료하고 다음 역할은 새 호출이다.
