## 1. 문제 정의

AI 코딩 에이전트로 실제 프로젝트를 굴릴 때 반복적으로 무너지는 지점:

| # | 문제 | 증상 |
|---|---|---|
| P1 | 세션이 끝나면 맥락이 사라짐 | 매 세션 앞부분을 재설명에 낭비. 이미 기각한 대안을 다시 제안함 |
| P2 | 기획 없이 바로 코딩 | 절반쯤 만들고 나서 요구사항이 틀렸음을 발견 |
| P3 | 세션 중단 시 재개 불가 | "어디까지 했더라"를 코드에서 역추적해야 함 |
| P4 | 검증이 자기확인 | 만든 에이전트가 "잘 됐습니다"라고 자평. 실제로는 미충족 |
| P5 | 보안이 사후 처리 | 다 만들고 나서 스캔 → 구조적 결함은 이미 고착 |

핵심 통찰 두 가지 (조사에서 반복 확인):
- **생성자 ≠ 검증자.** 에이전트가 자기 검증을 통제하면 그것은 검증이 아니다.
- **게이트는 실패할 수 있어야 한다.** 빨간불로 만드는 입력을 명시할 수 없는 게이트는 장식이다.

## 2. 목표 / 비목표

### 목표
- G1. 프로젝트 맥락을 파일로 영속화하고, 세션 시작 시 자동 주입
- G2. 구현 전에 조사·질문·스펙·위협모델을 강제하는 기획 파이프라인
- G3. 임의 시점에 세션이 끊겨도 다음 세션이 30초 안에 재개
- G4. 구현 컨텍스트와 분리된 독립 검증
- G5. 보안을 계획 단계부터 반영(위협 모델) + 커밋 전 자동 검사
- G6. 도메인 특화(임베디드 등)를 코어 수정 없이 오버레이로 추가

### 비목표
- 코드를 대신 짜주는 것 자체 (그건 Claude Code가 이미 함) — 하네스는 **절차와 상태**만 관리
- 프로젝트 관리 도구 대체 (지라/노션 대체 아님)
- 에이전트 간 완전 이식성 — v1은 Claude Code 전용 (§4 D-001)

## 3. 설계 원칙

1. **파일이 진실, 대화는 휘발성.** 대화에서만 합의된 것은 존재하지 않는 것으로 취급.
2. **맥락은 변경 속도로 계층화.** 전부 기억하려 하면 컨텍스트가 썩는다.
3. **모든 게이트는 빨간불 조건을 문서화한다.** 조건이 없으면 게이트가 아니다.
4. **질문은 예산이 있다.** 무한 질문은 사용자가 하네스를 버리게 만든다. 답을 추측해서 기본값과 함께 묻는다.
5. **비상구를 v1부터 넣는다.** 오타 수정에 7단계 파이프라인을 태우면 아무도 쓰지 않는다.

## 5. 아키텍처

### 5.1 컨텍스트 3계층

| 계층 | 내용 | 파일 | 주입 시점 |
|---|---|---|---|
| L0 불변 | 절대 원칙, 금지사항 | `CONSTITUTION.md` | 항상 |
| L1 저속 | 스택, 도메인 용어, 결정 이력 | `CONTEXT.md`, `GLOSSARY.md`, `DECISIONS/` | 세션 시작 |
| L2 고속 | 지금 어디까지 했나 | `STATE.md`, `JOURNAL.md` | 세션 시작 + 매 태스크 후 갱신 |

### 5.2 산출물 구조

**하네스는 코드 위치를 건드리지 않는다.** 앱 코드는 평소대로 `src/`에 생성되고,
하네스 산출물은 전부 `.interlocking/` 아래 문서로만 존재한다.

```
todo-app/
├── src/                        ← 앱 코드. 하네스 관여 없음
├── package.json
├── CLAUDE.md                   ← 얇은 부트로더: "STATE.md부터 읽어라"
└── .interlocking/                   ← ★ 하네스 산출물 (git 커밋)
    ├── profile.yaml            # domain: general|embedded / rigor: solo|team
    ├── gates.yaml              # 게이트별 "빨간불 조건"
    ├── CONTEXT.md              # 프로젝트 지식 (수명: 프로젝트 전체)
    ├── DECISIONS/ADR-0001-*.md # 무엇을 골랐고 무엇을 왜 버렸는가
    ├── work/001-login/         # 기능 하나의 작업 기록 (수명: 그 기능)
    │   ├── SPEC.md
    │   ├── PLAN.md
    │   ├── TASKS.md
    │   ├── STATE.md            # ★ 재개 앵커
    │   └── VERIFY.md
    └── archive/                # 완료된 기능 이동
```

**두 층의 차이는 수명이다.** `CONTEXT.md`·`DECISIONS/`는 프로젝트가 끝날 때까지 하나로 유지되고,
`work/<NNN>/`는 기능마다 새로 생겼다가 완료되면 `archive/`로 이동한다.

| 파일 | 내용 | 해결하는 문제 |
|---|---|---|
| `CONTEXT.md` | ① 불변 원칙(L0) ② 스택·제약·도메인 용어(L1) — 두 섹션으로 구분 | P1 |
| `DECISIONS/` | ADR. 채택안 + **기각한 대안과 이유** | P1 (기각안 재제안 방지) |
| `SPEC.md` | 배경·조사 근거(출처 포함) / **위협 모델** / `REQ-###` + 테스트 가능한 수용기준 / `ASM-###` 가정 원장 | P2, P5 |
| `PLAN.md` | 아키텍처·단계·기술 선택의 이유 (위협 모델은 SPEC으로 이동, D-012) | P2 |
| `TASKS.md` | `T-###` 원자 태스크. `state` / `covers`(REQ) / `depends` / **`produces`**(함수 시그니처·경로) / `verify`. **추가 전용** | P2, P4 |
| `STATE.md` | 재개 지점 + append-only 히스토리 | P3 |
| `VERIFY.md` | REQ별 PASS/FAIL, 검증자 소견, 스캔 결과 | P4 |

> 별도 파일로 뺐던 조사·가정·위협모델·추적성·저널은 위 문서의 섹션으로 접어 넣었다(D-008).
> `rigor: team`에서는 `CONTEXT.md`의 원칙 섹션을 `CONSTITUTION.md`로, 추적성을 `TRACE.md`로 분리할 수 있다.

`STATE.md` 형식 (재개의 심장):

```yaml
feature: 001-login
phase: EXECUTE
gates_passed: [G0-spec, G1-plan]
next_action: "T-012 구현 — src/auth/session.ts, 기준: SPEC.md#REQ-007"
blocked_on: null
open_assumptions: [ASM-002]
last_verified_commit: abc123
dirty_files: []          # 재개 시 미커밋 잔여물 (§5.10)
---
## History (append-only)
- 2026-08-15 G2 override — T-009, 사유: 테스트 인프라 미비
- 2026-08-15 T-010~T-011 완료, VERIFY.md 갱신
```

### 5.3 페이즈 & 게이트

```
INTAKE → RESEARCH → INTERVIEW ⇄ THREAT → SPEC → [G0] → PLAN → TASKS → [G1]
   → EXECUTE (태스크당 새 컨텍스트, 태스크=커밋) → VERIFY (독립) → [G2]
   → INTEGRATE → [G3] → ARCHIVE
```

**위협 모델은 SPEC보다 앞에 온다**(D-012). 완화책이 새 요구사항을 낳기 때문에,
PLAN 단계에 두면 이미 승인된 SPEC을 고쳐야 하고 G0 승인이 무효가 된다.

| 게이트 | 판정자 | 빨간불 조건 (gates.yaml) |
|---|---|---|
| **G0 스펙** | 사람 (**하드 차단**) | 수용기준이 테스트 불가능한 문장 / 위협모델의 완화책이 REQ로 환류되지 않음 / 미확인 가정이 승인 뷰에 노출되지 않음 |
| G1 계획 | 사람 | 태스크에 `produces` 또는 `verify` 미기재 / 어떤 REQ도 담당하지 않는 태스크 존재 |
| G2 검증 | 기계 훅 + 독립 검증자 | 테스트 실패 / lint·SAST·secret·CVE 스캔 실패 / REQ 수용기준 미충족 |
| G3 통합 | 사람 | REQ 중 담당 태스크가 없는 항목 존재 / 스펙-코드 드리프트 감지 |

G0만 `PreToolUse` 훅으로 코드 파일 편집을 물리적으로 차단한다(D-009). 나머지는 정지 + 우회 가능.

**태스크 상태 머신:** `TASKS.md`의 각 태스크는 `todo → doing → done | blocked` 상태를 가진다.
**태스크 1개 = 커밋 1개**를 원칙으로 하여, 세션이 임의 시점에 끊겨도 커밋 단위로 복원된다.
기계 검사(G2 훅)를 통과하기 전에는 `done`으로 전이 불가.

**패스트 레인:** 작업 크기 분류(`trivial` / `small` / `feature` / `epic`)에 따라 페이즈 스킵.
`trivial`은 EXECUTE + G2만. 스킵 사실은 `STATE.md` 히스토리에 기록.

**실패 경로:** 태스크 N회 연속 실패 시 자동 중단 → 원인 분석 문서 작성 → 사용자 에스컬레이션.
에이전트가 무한 재시도하며 코드를 망가뜨리는 것을 차단.
검증 FAIL 시에는 기존 태스크를 고치지 않고 **새 태스크를 append**하며, 원 태스크는 `blocked`로 되돌린다.

### 5.4 인터뷰 프로토콜 (기획 단계의 핵심)

무한 질문 금지. 대신:
1. 에이전트가 **먼저 조사**한다 (웹 + 기존 코드베이스) → `SPEC.md`의 배경·조사 근거 섹션 (출처 필수)
2. 조사 결과로 **답을 추측**하고, 기본값과 함께 묻는다 — "A로 가정했습니다. 맞나요? 아니면 B/C"
3. 라운드당 3~5문항, 최대 3라운드 (rigor=team이면 5라운드).
   **분기형으로 묻는다** — 한 번에 다 던지지 않고, 앞 답에 따라 다음 질문 집합이 갈라진다
   (예: "소셜 로그인 포함" → 프로바이더·계정 병합 질문이 열림 / "제외" → 그 가지는 아예 안 물음)
4. 질문 우선순위 = "이 답이 달라지면 **설계가 바뀌는가**"
5. 답 못 받은 항목은 `ASM-###`으로 가정 원장에 기록하고 진행.
   가정이 나중에 깨지면 어떤 REQ/태스크가 영향받는지 역추적 가능해야 함.
6. 사용자가 **"알아서 해"라고 답한 경우**에도 기본값을 채택하고 ASM으로 기록한다.
   "명시적으로 동의함"과 "답을 회피함"을 구분해 적는다 — 나중에 문제가 생겼을 때 책임 소재가 다르다.
7. **스펙을 쓰다가 새 미확인 가정이 생기면** 인터뷰를 다시 열지 않는다.
   가정 원장에 적고 **G0 승인 뷰에 "미확인 가정"으로 올려** 사용자가 승인 시점에 함께 답하게 한다.
   (walkthrough 구멍 #1 — 라운드를 늘리는 것보다 값싸다)

**게이트 승인 뷰:** 사용자에게 문서 전문을 들이밀지 않는다. G0은 20줄 요약(만들 것 / 안 만들 것 /
미확인 가정 / 전문 경로)으로 제시한다. 90줄짜리 스펙을 강요하면 아무도 안 읽고 그냥 승인한다.

### 5.5 프로파일 오버레이

```
core (페이즈, 게이트 골격, STATE 스키마)
  + domain overlay   : 체크리스트, 위협모델 템플릿, 검증 방법
  + rigor overlay    : 게이트 수, 인간 승인 지점, 인터뷰 라운드 수
```

- `domain: general` — 웹/서버/CLI 기본값
- `domain: embedded` (추후) — 메모리·스택 예산, 인터럽트 안전성, 하드웨어 의존 테스트 대체 전략, HIL 검증, 코딩 규칙(MISRA류).
  추가로 **하드웨어 지식 계층**: `.interlocking/hardware/` 에 부품 선정 근거, 핀맵, 인터페이스 사양, 데이터시트 링크.
  임베디드에서는 회로도·데이터시트·시뮬 결과도 코드와 동등한 맥락이므로 `CONTEXT.md`만으로는 부족하다.
- `rigor: solo` — G0/G1 승인을 한 번으로 병합, 패스트 레인 적극 사용
- `rigor: team` — 게이트 전부 활성, ADR·추적성 필수

### 5.6 Claude Code 프리미티브 매핑

| 프리미티브 | 용도 |
|---|---|
| `CLAUDE.md` | 얇은 부트로더. 규칙 나열 대신 "언제 어떤 스킬을 켜라"만 |
| **SessionStart 훅** | L0+L1+L2 주입 → **P1·P3 해결의 핵심** |
| **Stop 훅** | `STATE.md` 갱신 강제. 이게 없으면 재개가 무너짐 |
| **PreCompact 훅** | 컨텍스트 압축 **직전**에도 `STATE.md` 저장. 긴 세션에서는 종료보다 압축이 먼저 온다 |
| **PreToolUse 훅** | 위험 명령/경로 차단. **G0 미통과 시 코드 파일 편집 하드 차단**(D-009) |
| **PostToolUse 훅** | 포맷·lint·secret scan |
| Skills | 페이즈별 절차서: `interview` `plan` `execute` `verify` `security-review` `onboard` |
| Subagents | `researcher` / `executor`(태스크 1개, 깨끗한 컨텍스트) / `verifier`(구현 대화 미열람) / `security-auditor` |
| Commands | `/il:new` `/il:resume` `/il:next` `/il:verify` `/il:status` `/il:fast` `/il:override` |

### 5.7 보안 두 축

**(a) 만드는 것의 보안**
- PLAN 단계에 위협 모델링 (자산 → 위협 → 완화) → 완화책을 REQ로 환류
- G2에서 secret scan / SAST / 의존성 CVE 자동 검사

**(b) 하네스 자체의 보안**
- 프롬프트 인젝션 방어: 웹/이슈/외부 문서 내용은 **데이터이지 명령이 아님**을 스킬에 명문화
- 툴 권한 최소화, 위험 명령 차단 훅
- 서브에이전트가 읽을 수 있는 파일 범위 제한

### 5.8 실패 학습 루프 — 하네스가 쓸수록 좋아지는 장치

지금까지의 설계는 전부 "절차를 지키게 하는" 것이고, **경험이 축적되는 경로가 없었다.** 이를 추가한다.

```
에이전트가 삽질/실패
   → .interlocking/PITFALLS.md 에 "함정" 항목 기록 (증상 / 원인 / 회피법)
   → 같은 함정이 2회 이상 반복
   → CONTEXT.md 의 원칙 섹션으로 승격 (= 이후 모든 세션에 항상 주입)
```

- 기록 시점: 태스크 실패, G2 FAIL, 사용자의 명시적 교정 (`/il:pitfall`)
- 승격은 자동 제안 + 사용자 승인 (원칙 섹션은 항상 로드되므로 무분별한 증식 금지)
- 승격된 항목은 §5.9의 예산에 포함되어, 상한을 넘으면 오래된 규칙 정리를 요구

### 5.9 컨텍스트 예산

계층화만으로는 부족하다. **항상 로드되는 텍스트에 정량 상한**을 둔다.

| 대상 | 상한(초안) | 초과 시 |
|---|---|---|
| `CLAUDE.md` | 50줄 | 훅이 경고, 하위 문서로 이관 요구 |
| `CONTEXT.md` 원칙 섹션 | 40줄 | 승격된 규칙 정리 요구 |
| `CONTEXT.md` 전체 | 200줄 | 상세는 `DECISIONS/`로 이관 |
| `PITFALLS.md` | 100줄 | 오래된 함정 정리 |
| `STATE.md` | 60줄 | 히스토리 오래된 항목 접기 |

나머지 문서(`SPEC.md`, `PLAN.md`, `DECISIONS/`)는 상한 없음 — **필요할 때만 읽히는 문서**이므로.
"항상 로드"와 "필요할 때 로드"의 구분을 지키는 것이 이 하네스의 성능을 좌우한다.

**아카이브 규칙:** 기능 완료 시 `CONTEXT.md`에는 **한 줄 요약 + 아카이브 포인터만** 남긴다.
(예: `인증: 서버 세션 + HttpOnly 쿠키. 상세 → archive/001-login/`)
이 규칙이 없으면 기능이 20개 쌓였을 때 `CONTEXT.md`가 상한을 넘는다 (구멍 #8).

### 5.10 실행·검증 프로토콜

설계 단계의 walkthrough에서 확정된 실무 규약. 그 walkthrough가 찾아낸 "구멍 #1~#10"은
별도 문서로 남기지 않고 §4의 D-012~D-018로 흡수했으므로, 각 결정의 근거 칸에서 읽을 수 있다.
실제로 구현된 것을 한 바퀴 돌린 기록은 [`WALKTHROUGH.ko.md`](WALKTHROUGH.ko.md) 에 있다.

**태스크 위임 패킷** — 메인 세션이 서브에이전트에 넘기는 것 (이것만으로 자족적이어야 함):
```
① 역할 + 완료 조건        ② CONTEXT.md 발췌 (관련 규약만)
③ TASKS.md의 해당 태스크   ④ 담당 REQ + 수용기준 전문
⑤ 선행 태스크의 produces  ← 없으면 서브에이전트가 시그니처를 몰라 헤맨다
```

**반환 3줄 제한** — 서브에이전트는 요약 3줄 이내만 반환한다. 상세는 커밋과 `VERIFY.md`에 남는다.
제한이 없으면 태스크를 8개 돌린 뒤 메인 세션도 결국 오염된다.

**검증자 권한** — 읽기 + **실행** 허용, **쓰기 금지**.
실행 권한이 없으면 "응답 시간 차 50ms 이내" 같은 기준을 판정할 수 없고,
쓰기 권한이 있으면 검증자가 아니라 두 번째 구현자가 된다.

**재개 시 미커밋 잔여물** — `STATE.md`의 `dirty_files`로 감지하고,
**"이어서 완성 / 버리고 재시작"을 반드시 사용자에게 묻는다.** 자동 판단 금지 (작업 소실 위험).

**훅은 검사만, 판단은 에이전트가** — 셸 스크립트는 "`STATE.md`를 적절히 갱신"할 수 없다.
`Stop` 훅은 `next_action`이 이번 세션의 마지막 커밋보다 오래됐는지만 보고, 그렇다면 종료를 막고
에이전트에게 갱신을 요구한다.
